# Database Schema

The backend owns the database schema because it is the source of truth for the
application. The frontend should never talk directly to the database, and the AI
service should not save transactions. Spring Boot controls the data model,
validates requests, and decides when data is written.

For the first version, FinGuard needs two core tables:

```text
users
  one user can have many transactions

transactions
  each transaction belongs to one user
```

That relationship is called **one-to-many**:

```text
users.id -> transactions.user_id
```

## ID Strategy

We will use `BIGSERIAL` for the first version.

Why:

- It is simple for learning.
- PostgreSQL automatically generates increasing IDs.
- It works nicely with Spring Data JPA.
- It is easy to read during debugging.

Example:

```text
User 1 owns transactions 10, 11, and 12.
```

Later, production fintech systems often use UUIDs because they are harder to
guess and safer across distributed systems. For this learning project,
`BIGSERIAL` keeps the first implementation clearer.

## users

| Column | Type | Notes |
| --- | --- | --- |
| id | BIGSERIAL | Primary key generated by PostgreSQL |
| username | VARCHAR(50) | Required and unique |
| email | VARCHAR(255) | Required and unique |
| password_hash | VARCHAR(255) | Required hashed password, never plain text |
| created_at | TIMESTAMP | Account creation time |
| updated_at | TIMESTAMP | Last time the user row changed |

### Why These Columns Exist

`id` is the internal database identity. Other tables should reference this,
not `username` or `email`, because usernames and emails can theoretically change.

`username` is a human-friendly login/display identifier. We make it unique so
two users cannot claim the same name.

`email` is also unique because it is normally used for login, password reset,
and account communication.

`password_hash` stores the result of hashing a password with a secure algorithm.
The actual password should never be stored. If the database leaks, hashed
passwords reduce the damage.

`created_at` and `updated_at` help audit data. In real systems, knowing when a
record was created or changed is very useful for debugging and compliance.

## transactions

| Column | Type | Notes |
| --- | --- | --- |
| id | BIGSERIAL | Primary key generated by PostgreSQL |
| user_id | BIGINT | Foreign key to `users.id` |
| amount | DECIMAL(12,2) | Required transaction amount |
| category | VARCHAR(80) | Required spending category |
| merchant | VARCHAR(120) | Required merchant or payee name |
| transaction_time | TIMESTAMP | When the transaction happened |
| is_flagged | BOOLEAN | Whether the AI service marked it suspicious |
| risk_score | DOUBLE PRECISION | AI risk score between 0.0 and 1.0 |
| created_at | TIMESTAMP | When the row was saved |

### Why These Columns Exist

`user_id` connects the transaction to its owner. This is the foreign key.
Without it, we would not know which user made which transaction.

`amount` uses `DECIMAL(12,2)` instead of `FLOAT` because money should not be
stored using floating-point arithmetic. Floating-point numbers can introduce
small precision errors. `DECIMAL(12,2)` means up to 12 total digits, with 2
digits after the decimal point.

`category` lets us group spending, such as Groceries, Entertainment, Travel, or
Utilities. This will later help the dashboard and AI feature engineering.

`merchant` stores where the money was spent. This can help users recognize
transactions and can become useful for risk analysis later.

`transaction_time` is the actual time of the transaction. We avoid naming the
column just `timestamp` because `timestamp` is also a SQL type, and using it as a
column name can be confusing.

`is_flagged` is the simple yes/no result shown to the user.

`risk_score` is the detailed AI result. For example, `0.10` means low risk and
`0.87` means high risk. The backend saves both `risk_score` and `is_flagged` so
the frontend does not need to call the AI service directly.

`created_at` records when our system saved the transaction. This can differ from
`transaction_time`; for example, a user might enter yesterday's transaction
today.

## Constraints

Constraints are database rules that protect data quality.

```sql
users.username must be unique
users.email must be unique
transactions.user_id must reference an existing user
transactions.amount must be greater than 0
transactions.risk_score must be between 0 and 1
```

These rules matter because they protect the database even if a bug appears in
the backend code.

## Indexes

Indexes make common reads faster. They are like a lookup map inside the
database.

Recommended first indexes:

| Index | Why |
| --- | --- |
| users.username | Fast username lookup during login |
| users.email | Fast email lookup during login/account flows |
| transactions.user_id | Fast lookup of a user's transactions |
| transactions.user_id + transaction_time | Fast dashboard/history queries in date order |
| transactions.user_id + is_flagged | Fast lookup of suspicious transactions |

We should not add random indexes everywhere. Indexes speed up reads but add a
small cost to writes, because PostgreSQL has to update each index whenever data
changes.

## First Migration Preview

When we create the Spring Boot backend, this design will become Flyway migration
files similar to this:

```sql
CREATE TABLE users (
  id BIGSERIAL PRIMARY KEY,
  username VARCHAR(50) NOT NULL UNIQUE,
  email VARCHAR(255) NOT NULL UNIQUE,
  password_hash VARCHAR(255) NOT NULL,
  created_at TIMESTAMP NOT NULL,
  updated_at TIMESTAMP NOT NULL
);

CREATE TABLE transactions (
  id BIGSERIAL PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users(id),
  amount DECIMAL(12,2) NOT NULL CHECK (amount > 0),
  category VARCHAR(80) NOT NULL,
  merchant VARCHAR(120) NOT NULL,
  transaction_time TIMESTAMP NOT NULL,
  is_flagged BOOLEAN NOT NULL DEFAULT FALSE,
  risk_score DOUBLE PRECISION NOT NULL DEFAULT 0 CHECK (risk_score >= 0 AND risk_score <= 1),
  created_at TIMESTAMP NOT NULL
);
```

We are not adding these migrations yet. Step 2 is about understanding and
documenting the design first.
